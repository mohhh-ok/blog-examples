# Irodori-TTS v4.1-Small: 台本を 1 行ずつ合成したとき、行の境目で声が変わるか

JVS コーパスの 10 人と リポジトリ所有者 (mo) の R10 の計 11 声、参照の品質 3 条件、合成方式 3 通りで計測した (2026-10-07)。

## 結論

1. **1 行ずつで崩れる条件は無かった。** 以前 Fish Audio で 1 行ずつ合成して行の境目で声が別人に入れ替わったときの値 (行の ref 比 mean 0.71〜0.74 / std 0.10〜0.15、別人の行 0.4〜0.6、男声の参照から 401Hz / 481Hz の行) に当たる条件は、99 条件 (11 声 x 3 品質 x 3 方式) のどれにも無い。per-line の 66 条件で、行の ref 比の最小は 0.6395、条件内 std の最大は 0.0651、行の F0 中央値と参照の F0 のずれは最大 5.7 半音 (1 オクターブは 12 半音)。
   - ref 比 0.75 未満の行は 660 行中 55 行。そのうち 49 行が 1 行目「京都へようこそ。」(29 行) と 5 行目「次は嵐山です。」(20 行) で、音声が 2 秒前後の最も短い 2 行。残りは 3 行目 3 行、9 行目 3 行
2. **seed を全行で固定しても、行間の一貫性は上がらなかった。** 同じ声・同じ品質の 33 組で比べると、条件内 std が固定のほうが小さかったのは 17 / 33 組、行どうしのペア類似度の平均が固定のほうが高かったのは 11 / 33 組。11 声の平均では std 0.0409 / 0.0389 / 0.0482 (固定、clean / quiet / noisy) に対し 0.0396 / 0.0422 / 0.0443 (ランダム)
3. **run (5 行ずつ 1 回で合成) も崩れなかったが、1 行ずつより一貫するわけでもなかった。** 3 方式を同じ単位 (前処理後の音声をつないだ 2.5 秒窓) で測ると、ref 比の平均 0.7988〜0.8170、窓の std 0.0256〜0.0283、0.75 未満の窓の割合 7.2〜12.7% (最も多いのは noisy の run で 12.7%)。同じ品質の中での方式による ref 比平均の差 (clean 0.0022、quiet 0.0039、noisy 0.0045) は、品質による差 (clean と quiet で 0.0121〜0.018) より小さい (表 2)。run の窓の std は per-line より小さくない (clean: run 0.0273 / per-line-random 0.0261)
4. **quiet (参照を -25 dB) は効き方が小さい。** Irodori は参照を合成前に -16 dB へ正規化する (`SamplingRequest.ref_normalize_db=-16.0` が既定。生成ログ "reference loudness normalize enabled per clip (target_db=-16.00, includes peak safety scaling).")。それでも ref 比の平均は clean より下がった (行単位 per-line-random: clean 0.8375 → quiet 0.8176、窓単位: 0.817 → 0.8005) が、崩壊には至らない。実運用でも Irodori に渡す参照は同じく正規化されるので、実運用に近い条件
5. 声による差は方式による差より大きい。per-line-random clean の ref 比の平均は jvs061 0.784 / jvs084 0.7925 から jvs041 0.8849 / mo 0.8946 まで (表 3)。その調査でのクリーンな参照のベースライン (Fish、ref 比 0.92±0.01) より全体に低く、0.75 の線は Irodori + JVS では「崩れ」の目安にならない (崩れていない run でも 2.5 秒窓の 7〜13% が 0.75 未満)

実運用への意味 (Claude の判断): 声の入れ替わりという点では 1 行ずつ合成で足り、run 結合を入れても一貫性は上がらない。ただし最も短い行 (2 秒前後) の ref 比が低く出やすいので、耳で確かめるときは 1 行目・5 行目を聴く。

run を 2 回に分けた理由 (preflight): 10 行を 1 回にした文は 103 トークンで入力上限 256 には収まるが、jvs016 clean で予測尺が 880.7 フレーム (35.2 秒) になり、出力上限 750 フレーム (30.000 秒) に切り詰められた ("predicted duration frames=880.7, scale=1.000, using_frames=750 (30.000s).")。2 回に分けた run 66 本の長さは r1 18.92〜24.68 秒、r2 25.44〜30.0 秒。上限に当たったのは jvs041 quiet r2 の 1 本だけで、予測 750.1 フレームに対して 750 フレーム (差 4 ミリ秒)。

## 測り方

Fish Audio で声が入れ替わったときの調査と同じく、resemblyzer (VoiceEncoder、256 次元) のコサイン類似度。

- 行単位 (measure.py、pod の GPU): per-line は各行まるごとの ref 比と、同じ条件の 10 行どうしの全 45 ペア。run は前処理 (16kHz、無音除去) 後の音声を 2.5 秒窓 / 1.0 秒ホップで切った各窓の ref 比と窓どうしのペア
- 同じ単位 (measure_windows.py、ローカルの CPU): 行単位では per-line (1.8〜9.4 秒の 1 行) と run (2.5 秒窓) で測る長さが違い比べられないため、3 方式とも前処理後の音声を順につないで (per-line は 10 行、run は r1・r2) 2.5 秒窓 / 1.0 秒ホップで測り直した。行の境目をまたぐ窓も入る。CPU と GPU の差の確認: mo clean run の窓の ref 比平均は pod 0.8405 (33 窓) / ローカル 0.8438 (35 窓、r1 と r2 の境目をまたぐ 2 窓が増える)
- F0: Praat の自己相関法 (parselmouth 0.4.7 の `to_pitch_ac`、16kHz、0.016 秒刻み、50〜800Hz) の有声フレームの中央値。参照も同じ方法。librosa.pyin は pod の numba 0.63.1 + numpy 2.2.6 で Segmentation fault になったため使っていない
- 0.75 は Fish で声が入れ替わったときの行の mean (0.71〜0.74) を目安にした線。「別人」の区間はそのとき 0.4〜0.6

## 聴き比べ用の音声

手元で `<声>-<品質>-<方式>.wav` (99 本) を作って聴いた。per-line は 10 行を、run は r1・r2 を、間に 0.4 秒の無音を挟んでつないだもの。生成音声の全件 (726 本) と参照はリポに入れていない。mo の clean 3 方式だけ `output/` に置いた。
