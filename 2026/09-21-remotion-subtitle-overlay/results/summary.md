- GCE `n2-standard-4` (4 vCPU / 16GB、Intel Xeon 2.80GHz)、Debian 12。同じ構成の VM を 3 台 (vm-a / vm-b / vm-c) 使い、条件を分けて並列に回した
- bun 1.4.2、Remotion 4.0.459、Chrome Headless Shell (Chromium 149.0.7790.0)、ffmpeg 5.1.9 (apt。overlay に使用。Remotion 内部のエンコードは同梱の ffmpeg n7.1)
- 1080x1920、30fps。値は「動画 1 秒あたりの処理秒数」(小さいほど速い)。`concurrency` の `default` は Remotion の既定値
- 生の値は `gce-n2-standard-4/` 以下の JSON (ブラウザログは削ってある)

VM 間の差の確認: X (60 秒・concurrency 1) を 3 台で測り、vm-a 9.13〜9.20 / vm-b 9.03 / vm-c 8.94。差は約 3% 以内。

- Y は 20 分にすると 60 秒のときより約 3 割遅い。原因は未調査
- Z-prores は尺に比例する
- 20 分の Z-prores は途中で打ち切った (`vm-c/long.json` に error つきで残っている。集計から除く)。20 分の Z-vp9 と X は測っていない
- ProRes 4444 の中間ファイルは 60 秒で 269MB、5 分で 1.35GB

## 読み取れること

- 字幕を描くこと自体のコストはほぼゼロ (X と P が同じ)
- 透過 webm 1 本のコストは約 1.9 秒/秒 (X − W)。全体の 2 割
- 動画を 1 本も読まない Z でも 5.6〜6.5 秒/秒かかる。全フレームを Chromium で描いてキャプチャし、透過つきでエンコードする部分が支配的
- どの作り方でも X からの削減は 2〜3 割にとどまる
- `<Video>` は GPU の無い Linux ではソフトウェア WebGL で動き、`OffthreadVideo` の 2.2 倍遅い。macOS では WebGL2 が取れず `OffthreadVideo` にフォールバックした
- macOS (5 秒の動作確認) では ProRes の描画が VP9 の約 1/5 の時間だったが、この Linux 環境では ProRes のほうが遅い。環境で順位が入れ替わる
